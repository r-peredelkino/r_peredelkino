# Солнечная теневая камера v31

## Интеграция

```js
import {
  collectSolarShadowBounds,
  createSolarShadowCameraFitter,
} from './solar-shadow-camera.js';

// Один раз после создания модели; не каждый кадр.
const bounds = collectSolarShadowBounds(model.root);
const shadowFit = createSolarShadowCameraFitter(sun, bounds);

// После изменения камеры или положения Солнца.
shadowFit.fit({ camera, direction: solarDirection });

// Если исходная геометрия изменилась или объект вышел за прежний envelope.
shadowFit.setBounds(collectSolarShadowBounds(model.root));
```

Для отдельного проверяемого участка можно передать `receiverBounds: Box3`
в `fit`. Это ограничивает только получателей теней; диапазон глубины
остаётся рассчитанным по всем затеняющим объектам. Изменение границ
получателей должно соответствовать выбранной области анализа.

## Математическое основание

Для параллельного света от Солнца точка поверхности `P` и затеняющий
её объект `P + t*S`, где `S` — единичный солнечный вектор, имеют одинаковые
координаты X/Y в системе теневой камеры. Различается только глубина.

Поэтому камера подбирается в двух независимых частях:

1. По X/Y охватывается пересечение frustum основной камеры и общего
   трёхмерного объёма получателей теней. Сохраняется вся их высота,
   включая видимые верхи зданий.
2. По глубине охватываются **все** предварительно собранные затеняющие
   объекты, а также видимые получатели. Низкое солнце не приводит
   к обрезанию дальнего источника тени фиксированными near/far.

Пересечение AABB и frustum строится отсечением обоих наборов из
12 рёбер. Это покрывает вершины исходных объёмов и пересечения
ребра одного объёма с гранью другого. Каждый следующий fit работает
с максимум 48 конечными точками, восемью углами caster AABB и
матрицами камер. Он не перебирает миллионы треугольников.

`collectSolarShadowBounds` выполняет один обход модели. Для обычной
геометрии используются её bounding box и world matrix; для экземпляров
учитываются все instance matrices. По умолчанию включены скрытые
сезонные объекты, чтобы зимние варианты не вышли за записанные границы.
Невалидные бесконечные границы отклоняются с ошибкой.

Центр тени привязан к сетке texel в light space. Размеры округляются
вверх шагом 2,5%; небольшое уменьшение удерживается гистерезисом,
а расширение выполняется немедленно. Дополнительный запас в два texel
не позволяет этому округлению отсечь поверхность у границы.

Сам солнечный вектор нормируется, но **не растягивается, не наклоняется
и не подгоняется по изображению**. Положение камеры вдоль него
выбирается перед всеми caster/receiver bounds.

## Проверки

```bash
node tools/qa-v31/shadow-camera-check.mjs
```

Сохранённый результат: `shadow-camera-check.json`, **PASS, 59 проверок**.

- Шесть камер: общий вид, сверху, прогулка в двух направлениях,
  взгляд вверх и вид из квартиры.
- Девять положений Солнца: летний и зимний полдень, утро, высота
  0,25° по четырём направлениям, зенит и положение ниже горизонта.
- Ни одной отсечённой контрольной точки получателя теней.
- Все углы полного caster volume попадают в диапазон near/far.
- Для 60 000 независимо сгенерированных точек 2699 оказались в
  видимом объёме; все они попали в тень по X/Y/Z.
- Максимальное расхождение light-space X/Y вдоль параллельного
  солнечного луча: `1.26e-13`.
- Максимальное расхождение установленного направления света:
  `4.64e-14`.
- Проверены sub-texel стабильность, instance bounds под поворотом
  и переносом родителя, обновление границ и отклонение плохих входов.

Для проверки глубины тест специально добавляет синтетические дальние
объекты. Их координаты не являются заявлением о геометрии района.
Исходные границы реальных модельных башен и 11 OSM-соседей записаны
в JSON отдельно.

## Качество и ограничения

Метод исправляет **покрытие и направление** shadow map. Он не повышает
достоверность исходной геометрии и не устраняет дискретизацию GPU.
Для прогулки с far=900 единиц world охват всех видимых поверхностей может дать
примерно 0,3–0,43 единицы world на texel при карте 4096². Это шире,
чем прежняя обрезанная камера +/-66, поэтому мелкие ближние тени
могут стать менее детальными. Одновременная высокая детализация
ближнего и дальнего плана требует каскадных карт теней либо другого
многоуровневого метода.

Независимая проверка фактической сцены, записанная в
`performance-shadow-camera-review.json`, показала ещё более широкий
случай: при пешей камере с far=2200 получатель-подложка леса имеет
world XZ от −3677,082 до +3677,082. Охват такого frustum даёт
ширину 3211,471 единицы и 0,78405 единицы на texel карты 4096².
При исходном ракурсе площади достаточно ширины 252,433 единицы
и 0,06163 единицы на texel. Это реальное ограничение разрешения
одной карты, а не ошибка подбора матриц.

Поэтому интеграция должна явно задать область получателей для
рассматриваемого квартала/прогулки либо использовать каскады. Нельзя
ради резкости неявно отрезать высоту зданий или менять солнечный угол.
Глубина затеняющей геометрии остаётся полной при любой области
получателей: удалённые здания продолжают отбрасывать тени на участок.

Для v31 согласован явный выбор **«Квартал (детальнее) / Район (шире)»**.
Обе области построены по фактическим группам сцены и сохраняют всю
высоту зданий. Квартал включает roadside перед участком; район —
все соседние дома, улицы и метро. В отдельном виде квартиры получателем
служит её полный объём. Полная затеняющая геометрия используется
при каждом варианте. Численный расчёт солнечных часов в точке не
ограничивается выбранной областью GPU-теней. Точные bbox, алгоритм
сбора, проверка far=900/1400 и результаты 420 сочетаний приведены
в `shadow-camera-regions.md` и `shadow-camera-regions.json`.

Обнаружен и отдельный источник лишнего вертикального охвата:
`complex-life.js` присваивает `receiveShadow=true` всем батчам, включая
`bucket.sky` с декоративными облаками на y≈140–169. Скрытые облака
при консервативном сборе тоже учитываются. Их следует исключить из
архитектурных получателей, не исключая скрытые сезонные деревья и
здания. В интеграции v31 это исправлено при создании `bucket.sky`:
receiveShadow=false и excludeFromSolarShadow=true. Сам helper
не изменяет флаги исходных объектов.

Точные солнечные часы в контрольной точке должны рассчитываться
проверкой видимости в сцене, а не считыванием пикселей shadow map.
Текстуры прозрачных листьев, туман, материал стекла и художественная
интенсивность света не заменяют геометрическую проверку прямого солнца.

После конструктивной интеграции нужен GPU-просмотр v31 на целевом Mac:
проверка исчезновения старых обрезаний, качества близких теней,
времени кадра, переключения дня и видов камеры. Этот документ
не объявляет такую интеграционную проверку уже выполненной.
